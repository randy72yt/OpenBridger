## 0. 一页结论

两套「分组」不是一回事，不能混用。

| 名字 | 存在哪里 | 今天的值 | 决定什么 |
|---|---|---|---|
| 销售分组 | 我们的用户、令牌、`channels.group`、`abilities.group` | `default`、`pro`。`GroupRatio` 现网记录为 `{"default":1,"pro":1}`（`docs/openbridger/pricing-plan-v2.3.md` §0，2026-11-10 核对，本次未再读库） | 这个用户能不能选到这条渠道，以及售价乘多少 |
| 上游分组 | dddai 上那把密钥自己的 `group` | 现在唯一渠道 #1 的密钥是 `auto` | dddai 用哪个池子、按哪个 `group_ratio` 扣我们的钱 |

我们的 NewAPI 适配器（渠道类型 60）只送 `Authorization: Bearer <key>`，不送分组头（`relay/channel/newapi/adaptor.go:39-56`）。上游分组钉死的办法，是在 dddai 上把**那把密钥的 group** 设成目标分组，然后在我们这边做成**一条独立渠道**。`header_override` 不能当成「请求级改上游分组」来用，除非以后用真实请求证明 dddai 认某个头。本次没有做这个实验。

`auto` 这个词在两边都出现，含义相反：

- 我们令牌的 `group=auto`：在**销售分组**之间按 `AutoGroups` 顺序换（`service/channel_select.go:115-184`）。
- dddai 密钥的 `group=auto`：在**上游分组**之间按对方的 `auto_groups` 换。2026-11-10 的顺序是 `codex-plus, default, openai-luna, grok, media, gemini, deepseek, glm, kimi, claude-kiro, claude-max`。第一个是可能降质的 `codex-plus`（0.15），第三个 `openai-luna` 是 1.1，大约是 `default`（0.23）的 4.8 倍。

所以今天「一个模型、一把 auto 密钥」同时有两个问题：质量由对方的 auto 顺序决定，成本由对方当时落到哪个分组决定。我们的定价采集默认并不知道这次请求会落在哪一组。

建议的合作方式：

1. **一个上游站点 × 一个钉死的上游分组 × 一把密钥 = 我们的一条渠道。** 不同价格的分组不要塞进同一条渠道的多密钥。
2. **同一销售分组里，同一模型只挂「价格已被售价覆盖」的渠道。** 贵的分组不要做成低优先级自动回退。优先级只用来做「同价备用」或「同分组第二把密钥」。权重只在同一优先级里分摊流量。
3. **售价仍是每个模型一份**（计费表达式 × 销售分组倍率）。`default` 和 `pro` 倍率都是 1，所以两边付一样的钱。pro 如果走到更贵的上游分组，毛利变薄，必须单独算过，不能靠「主渠道便宜」把备用渠道的亏损平均掉。
4. **`PRICING_AUTO_PUBLISH` 保持关闭。** 提案里的发布会把表达式写成两段式 `tier("base", p * … + c * …)`，丢掉缓存和长上下文（`service/pricing_control.go:840-845`）。现网 v2.3 是手写表达式。多渠道上线改的是采购成本告警，不是自动改售价。
5. **上线前的可靠性靠「按模型族拆渠道 + 同分组第二把密钥」，不靠把 RetryTimes 调大，也不靠贵分组兜底。** 代码里的重试在优先级用完之后会**夹在最低优先级上继续抽**，不会自动换一条更贵的渠道（`model/channel_cache.go:165-167`）。`RetryTimes` 代码默认是 0（`common/constants.go:134`）。

## 1. 今天一次请求怎么选渠道

下面是 `main` 上的实际路径。销售分组记为 G，模型记为 M。

### 1.1 销售分组从哪来

`middleware/auth.go:468-485`：

- 用户分组来自用户缓存 `user.Group`。
- 令牌 `token.Group` 非空时，必须落在该用户的可用分组里，并且 `GroupRatio` 里有这个名字。例外是令牌分组等于字符串 `auto`：它不必出现在 `GroupRatio` 里。
- 令牌分组为空：`UsingGroup = 用户分组`（default 或 pro）。
- 令牌分组非空：`UsingGroup = 令牌分组`（可以是 `auto`）。

`middleware/auth.go:513-523` 把 `token.CrossGroupRetry` 和令牌自己的 `auto_groups` 快照放进上下文。令牌没有快照时，`service/group.go:97-106` 退回全局 `AutoGroups`，再按「该用户是否可选、该分组是否在 GroupRatio 里」过滤。

代码默认的可用分组是 `default` / `vip`，默认 AutoGroups 只有 `default`（`setting/user_usable_group.go:10-13`，`setting/auto_group.go:13-16`）。现网记录已经改成 `default` / `pro`。**本次没有读生产 options。** 上线前要在控制台看三处是否一致：`GroupRatio`、用户可用分组、`AutoGroups`。残留的 `vip` / `svip` 不会自动消失。

### 1.2 第一次选渠道

`middleware/distributor.go:100-185`：

1. 令牌如果开了模型白名单，M 不在名单里直接 403。
2. 若有渠道亲和（affinity）且那条渠道仍启用、仍满足过滤器、并且在当前销售分组（或 auto 会走到的某个销售分组）里对 M 启用，就固定用它。亲和失败且策略不允许保留时，清掉亲和缓存。
3. 否则 `service.CacheGetRandomSatisfiedChannel`，重试次数从 0 开始。
4. 没有渠道：503，错误码 `model_not_found`。

选中后 `middleware/distributor.go:606-683` `SetupContextForSelectedChannel` 写入渠道 id、类型、`model_mapping`、`header_override`、`param_override`、`auto_ban`，并取下一把可用密钥。类型 60 没有单独分支，不会在这里设置上游分组。

### 1.3 能力表：销售分组 × 模型 → 渠道

渠道保存时，`model/ability.go:217-242` `AddAbilities` 把 `channels.models` 和 `channels.group`（逗号分隔）叉乘。每一对 `(销售分组, 模型)` 一行，带上该渠道的 `priority`、`weight`、`enabled`（渠道状态为启用才是 true）。

`setting/ratio_setting/model_pool.go:32-46` `ModelPoolAllows`：只有「基础池模型列表」和「高级分组列表」**都非空**时才拦截。基础池里的模型对所有销售分组开放；基础池外的模型只对 `premium_groups`（计划中的 pro）开放。两个列表有一个为空，则全部分组全模型，等于没门禁。门禁在**重建能力**时生效，所以后来的模型同步不会把被挡住的组合写回去。

内存缓存开启时（`MEMORY_CACHE_ENABLED=true`，代码默认是 false，`common/init.go:88`），`model/channel_cache.go:55-78` 用启用中的渠道重建 `group → model → []channelID`，按优先级从高到低排序。关闭时走数据库 `model/ability.go:109-165` `GetChannel`，条件同样是 `enabled = true`。

**同名模型出现在多条渠道上是路由需要的，不是脏数据。** 另一位代理要做的「同步时剪掉已下架和重复的渠道模型」，指的是**一条渠道的 models 字符串里**上游已经没有的名字、以及同一条字符串里的重复项。不要把跨渠道的同名模型剪掉。

### 1.4 优先级和权重

`model/channel_cache.go:117-216` `GetRandomSatisfiedChannel`（内存缓存路径；数据库路径在 `model/ability.go:121-158`，规则同类）：

1. 先按销售分组 + 原始模型名找渠道 id。没有则用 `ratio_setting.RoutingMatchModelName` 再找一次（去掉路由用的修饰名）。**这里不看 `model_mapping`。** 映射发生在选中渠道之后（`relay/helper/model_mapped.go:14-68`）。
2. 把候选按 `priority` 去重，从高到低排序。`retry` 是下标：0 = 最高优先级，1 = 次高，以此类推。
3. **`retry >= 优先级层数` 时，下标被夹到最后一层（最低优先级），不会返回空。** 于是多出来的重试仍在最低那一层里抽。
4. 在目标优先级内按权重随机。权重全是 0 时，每条渠道的有效权重被当成 100，均匀抽。平均权重小于 10 时有平滑系数。某条权重为 0、同层又有正权重时，0 权重那条减量为 0，循环可能走完仍选不中，返回 `channel not found`（`model/channel_cache.go:188-216`）。**不要用 0 权重表示「备用」。** 要分摊流量就用相等的正整数。

权重只在**同一优先级**内比较。不同价格的渠道如果放在同一优先级，流量按权重混打，贵的那条会按比例吃掉毛利。不同价格必须不同优先级，而且低的那层必须单独通过毛利底线，否则不要挂上。

### 1.5 失败后的重试

预扣费在重试循环**之前**做一次（`controller/relay.go:158-173`）。循环是 `controller/relay.go:196-246`：

```
for retry <= RetryTimes {
  选渠道 → PrepareTieredBillingForSelectedGroup → 转发
  成功就 return
  失败则 processChannelError，再 shouldRetry
}
全部失败：若 Billing 会话还在，Refund 预扣费
```

`shouldRetry`（`controller/relay.go:365-395`）：

- 渠道错误（`IsChannelError`）会重试。
- 标了 skip-retry 的不重试（读 body 失败、计费错误、没有渠道等）。
- 剩余次数 `RetryTimes - 当前retry <= 0` 时不重试。
- HTTP 2xx 不重试。
- 504 和 524 **永远不重试**（`setting/operation_setting/status_code_ranges.go:31-34`）。
- 其余按 `AutomaticRetryStatusCodeRanges`：含 401–407、409–499、500–503、505–523、525–599。**400 和 408 不在默认重试范围内。**

默认 `RetryTimes = 0`（`common/constants.go:134`）。现网是否改过，本次没读 options。0 的意思是循环只跑第 0 次，失败不换渠道。

重试**不会记住已经用过的渠道 id**。同一优先级里只有一条渠道时，每次重试还是它。有多条时按权重再抽，可能抽回刚才失败的那条。

销售分组 `auto` 且令牌开了 `cross_group_retry` 时（`service/channel_select.go:132-178`）：当前销售分组的 `priorityRetry >= RetryTimes` 后，下一次改走下一个销售分组，并把重试计数拨回 0。这换的是**我们的** default/pro，不是 dddai 的上游分组。没开跨分组重试时，失败后留在选中的那个销售分组里，直到外层 `RetryTimes` 用完。某个销售分组在当前优先级**根本没有**该模型的渠道时，不论跨分组开关，都会试下一个销售分组。

亲和规则可以要求失败后不重试（`service/channel_affinity.go` 的 `SkipRetryOnFailure`）。上线前看一下现网有没有把这条打开。

### 1.6 流式中途失败不会换渠道

OpenAI 兼容流的处理在 `relay/channel/openai/relay-openai.go:103-194`。扫描结束后**固定 `return usage, nil`**。没有 usage 块时，用已收到的文本本地估算 completion，prompt 用请求前的估算（`ResponseText2Usage`）。类型 60 在 `streamSupportedChannels` 里（`relay/common/relay_info.go:379`），我们会尽量让上游带 `include_usage`，但上游不给时就走估算。

后果：流已经开始之后，上游断开或中途报错，这一跳在我们这边仍是成功。用户拿到截断结果并被扣费，**不会**换下一条渠道，也**不会**因为这次中途错误去自动禁用渠道。自动回退只覆盖「响应头之前就失败」的情况。

### 1.7 自动禁用和重新启用

`controller/relay.go:397-405`：`ShouldDisableChannel` 且该渠道 `auto_ban` 为真，才异步禁用。

`service/channel.go:45-65`：总开关 `AutomaticDisableChannelEnabled` 代码默认 **false**（`common/constants.go:129`）。打开后，渠道级错误、状态码命中、或错误文本命中关键词，都会禁用。

默认状态码范围只有 **401**（`setting/operation_setting/status_code_ranges.go:17`）。默认关键词是余额不足、组织被禁、配额用尽、权限/令牌无效这类（`setting/operation_setting/operation_setting.go:8-16`）。**默认不会因为 503 禁用渠道。** 503 会重试（如果 `RetryTimes > 0`），但不会自动下线。2026-10-11 上游全模型 503 时，渠道不会被这套规则自己关掉；同时也没有任何备用渠道（`docs/openbridger/incidents/2026-10-11-upstream-route-intent-failure.md`）。

`GetAutoBan`：指针为 nil 时返回 false（`model/channel.go:343-347`），即使列的 gorm 默认是 1。没把 `auto_ban` 读出来的渠道不会被自动禁用。

禁用粒度：

- 单密钥渠道：整条渠道改为自动禁用，能力行 `enabled=false`（`model/channel.go:736-808`）。这条渠道上的**所有模型**一起不可用。一个模型的 401 会带走同渠道的其他模型。
- 多密钥渠道：只禁用用到的那把密钥；全部密钥禁用后，渠道状态才变成自动禁用（`model/channel.go:671-720`）。多密钥仍共享同一份 `models`、`priority`、`group`、定价报价。它适合「同一上游分组的多把密钥」，不适合「不同上游分组、不同价格」。

重新启用：`ShouldEnableChannel` 要求总开关 `AutomaticEnableChannelEnabled`、本次探测没有错误、且当前状态是自动禁用（`service/channel.go:67-77`）。探测在 `controller/channel-test.go:920-963`。定时任务默认关闭（`setting/operation_setting/monitor_setting.go:29-33`）。模式有三种：`scheduled_all`（默认，测所有非手动禁用的渠道）、`auto_ban_only`、`passive_recovery`（只测已自动禁用的，且这次探测**不允许**再禁用）。

探测只用**一个**模型：`TestModel`，否则 `models` 的第一个，再否则 `gpt-4o-mini`（`controller/channel-test.go:96-108`）。它解释不了「21/49 通过」。21/49 是目录级结果；渠道健康检查即使全绿，也只说明那一个测试模型通了。响应时间超过 `ChannelDisableThreshold`（代码默认 5 秒，`common/constants.go:128`）且允许禁用时，也会被当成失败并禁用。

内存缓存的一个洞：`model/channel_cache.go:251-274` `CacheUpdateChannelStatus` 在状态不是启用时，会把渠道从 `group2model2channels` 删掉。重新启用时只改 `channelsIDM` 里的状态，**不会把 id 插回路由表**。要等下一次全量 `InitChannelCache`。`SYNC_FREQUENCY` 默认 60 秒（`common/init.go:110`）。`MEMORY_CACHE_ENABLED` 默认 false。生产开没开，本次不知道。开着的话，自动恢复后最多大约一个同步周期内，这条渠道仍不会被选中。数据库路径没有这个延迟。

没有独立的熔断器。没有「滑动窗口错误率超过 N% 再摘除」。要么不禁用，要么一次命中关键词/401 就整条禁用。

### 1.8 计费用的分组倍率是销售侧的

`relay/helper/price.go:46-72` `HandleGroupRatio`：如果上下文里已经有 `auto_group`（销售侧 auto 选中的那个分组），`UsingGroup` 改成它。然后：

- 有 `GroupGroupRatio[用户分组][使用分组]` 就用这个特殊倍率；
- 否则用 `GetGroupRatio(使用分组)`。找不到键时打日志并返回 **1**（`setting/ratio_setting/group_ratio.go:79-85`）。

这个倍率乘的是**售价**，不是上游成本。上游 `group_ratio` 不参与这次扣费。

预扣费发生在选渠道之前，用的是当时的销售分组。选中渠道后 `controller/relay.go:356` 再算一次倍率，`service/tiered_settle.go:121-156` `PrepareTieredBillingForSelectedGroup` 按新倍率调整预扣：变贵就追加预扣，从免费分组切到付费分组才补开会话。全部失败才 `BillingSession.Refund`（`service/billing_session.go:82-90`）。成功则按**获胜那一跳**的 usage 结算，差额多退少补。失败的前几跳如果没有把响应标成成功，不单独扣费。

### 1.9 模型映射

`model_mapping` 是渠道上的 JSON，公开模型名 → 上游模型名，支持链式，检测环（`relay/helper/model_mapped.go:28-62`）。计费模型名用的是用户请求的原始名（或计费别名），不是映射后的上游名。报价同步反过来：上游名在映射表里时，记到对应的公开名上；同一个上游名有多条公开名时，保留先写进 map 的那条（`service/pricing_offer_sync.go:224-247`）。

两条渠道把同一个公开模型映射到不同上游模型时，售价仍是一份，成本却是两份。这种映射必须各自有报价，并且售价要盖住会真正被选中的那一份。

### 1.10 和上游分组无关的现有门禁

模型池（§1.3）是销售侧门禁，注释写明上游结算分组不得进这一层（`setting/ratio_setting/model_pool.go:7-15`）。这是对的。上游分组只活在「哪条渠道、哪把密钥」上。

## 2. 目标架构

### 2.1 映射规则

```
用户.group（default 或 pro）
  → 令牌.group 为空则用用户分组；为 auto 则在销售分组列表里走
    → abilities(销售分组, 公开模型) 里优先级最高、权重合规的渠道
      → 该渠道的 base_url + 密钥
        → 密钥在上游站点上的 group（我们发请求时改不了）
          → 上游按那个分组的 group_ratio 扣我们
```

销售分组决定「谁能用、按什么售价倍率付钱」。渠道决定「请求打到哪把密钥」。密钥在上游的分组决定「我们的成本」。三者要在配置时对齐，运行时没有第四个自动纠偏。

同一模型要对 default 和 pro 提供不同上游质量时：

- 做两条渠道，模型列表都包含 M。
- 便宜且可接受的那条：`group = default,pro`，优先级更高。
- 更贵、质量更好的那条：`group = pro`，不要同时写上 default。
- 售价仍是一份。pro 的成本更高、倍率仍是 1 时，毛利按贵的那条重算（第 3 节）。如果贵的那条会击穿底线，就不要给 pro 单独挂它，或者先把 pro 的 `GroupRatio` 提高（这是配置，会让 pro 的**所有**模型都变贵，不只是这一条）。

不要新建名为 `codex-plus` 或 `openai-pro` 的销售分组。那是采购分组。代码默认里的 `vip` 也不要复活。

### 2.2 dddai 建议布局

全部是类型 60，Base URL `https://api.dddai.dev`。每条渠道一把密钥，密钥在 dddai 上的 group 钉死。模型列表用「我们在售的模型 ∩ 该上游分组 `enable_groups`」。交集以同步结果为准，下表的「模型族」是根据 2026-11-10 的分组名做的归类，**不是**当次抓到的逐模型清单。`gpt-6-sol` 已确认同时出现在 `codex-plus` / `default` / `openai-pro` / `enterprise`，同一模型多价是事实。

优先级数字越大越先被选。同一层用权重。下表假定每个模型在每个销售分组里只有一个优先级，因此 `RetryTimes` 保持 0 也合理：没有第二层可换。同分组的第二把密钥放在**同一优先级**，用权重分摊，用来应付单把密钥 401 或余额耗尽；那时候要把 `RetryTimes` 至少设成 1，并且两把密钥都得有正权重。见第 7 节的待决问题。

### 2.3 以后加第二个上游站点

不需要新概念。第二个站点是另一组渠道：不同的 `base_url`，各自的密钥和钉死分组，公开模型名与现有渠道相同，这样能力表才能把它们当成同一 M 的候选。

| 角色 | 优先级 | 定价策略 |
|---|---|---|
| 热备用（主站挂了才用） | 比主站低一档，例如 80 | 策略里的备用渠道填它。售价必须按它的成本过底线，否则它一接流量就亏损。接不住就不要启用，只留着手动开。 |
| 同价分摊 | 与主站相同，权重分摊 | 策略的「主渠道」必须改成「同一优先级里更贵的那条」，见第 3 节。今天的策略只有一个 `primary_channel_id`，同优先级混打时提案会看错成本。在第 3 节的代码落地前，不要用权重把两个不同成本的站点混在同一优先级。 |

上游 B 在项目档案里仍是「未采用」（`docs/openbridger/project-profile.md` §7）。本方案不挑第二个供应商。

## 3. 成本与定价

### 3.1 今天一份成本怎么来

报价表 `upstream_model_offers` 的唯一键是渠道 id + 上游模型名 + 公开模型名（`model/pricing_control.go:34-38`）。一条渠道、一个公开模型，一行成本。

同步（`service/pricing_offer_sync.go`）：

1. 用该渠道的密钥 `GET` 定价端点，默认 `/api/pricing`，可被渠道设置 `pricing_endpoint` 覆盖。
2. 只保留渠道 `models` 里有的名字（含映射后的公开名）。
3. 基础价由倍率或计费表达式归一成每百万 token 的 USD。
4. 再乘一个结算倍率。挑选规则是环境变量 `PRICING_GROUP_RATIO_POLICY`（`service/pricing_offer_sync.go:311-322`）：
   - `key_group`：按响应里的 `auto_groups` 顺序，取模型 `enable_groups` 里第一个碰得上的。这接近「密钥本身是 auto」时对方的尝试顺序，**不是**「这把密钥被钉死在某一组」。
   - `max` / `min`：在该模型所有可用分组里取最大或最小。
   - 其他值，包括不设置：`median`。代码注释写明，max 曾把模型高估最多约 15 倍，median 是未钉死时的折中，有流量后由校准覆盖。
5. 校准优先于分组倍率（`service/pricing_control.go:345-360`）。校准用上游 `/api/log/token` 的实扣除以报价表理论成本（`service/pricing_calibration.go:22-29`）。它吸收了私有分组、缓存折扣、夜间系数这些报价表里没有的因素。样本不足就仍用分组倍率。

2026-11-04 的整改记录写生产 `.env` 是 `PRICING_GROUP_RATIO_POLICY=max`（`docs/openbridger/pricing-control-remediation-plan.md` 实施状态表）。**本次没有再读服务器 `.env`。** 若仍是 max，则在密钥还是 `auto` 时，成本偏保守（宁高勿低）；密钥钉死之后，max 会把「这把密钥碰不到的贵分组」也算进成本，售价会被抬高。钉死之后正确的倍率是**这把密钥的那一组**，不是 max，也不是 median。

这一步正是另一位代理在做的「按 `/api/pricing` 做有效上游分组解析」。本方案不另写一套。钉死渠道上线后，报价行上的 `upstream_group` 必须等于该密钥的分组，`upstream_group_ratio` 必须等于该分组（若有模型级 `model_group_ratio` 则用模型级）。在那之前，不要用现有的 max/median 去给已经钉死的密钥定价。

### 3.2 一个模型多条渠道时，提案用哪份成本

策略 `ModelPricePolicy` 只有两个槽：`primary_channel_id` 和可选的 `backup_channel_id`（`model/pricing_control.go:87-99`）。

`service/pricing_control.go:363-454`：

```
主成本 = 主渠道报价 ×（校准倍率或上游分组倍率）
备成本 = 备用渠道同样处理
期望成本 = 主成本 × (1 - p) + 备成本 × p
         p = fallback_probability_bps / 10000
压力成本 = 有备用时用备成本，否则用主成本
期望成本、压力成本再乘 (1 + overhead_bps/10000)
建议售价 = 期望成本 / (1 - target_margin_bps/10000)
```

只有 `service_tier == "stable"` 且存在备用渠道时，售价才取 `max(上面的建议价, 压力成本 / (1 - minimum_margin))`（同文件 425-428 行）。**default 档不看压力成本。** 发布进现网计费表达式的是 default 档（`PublishPricingProposal` 拒绝非 default，同文件 684-686 行）。

因此：

| 做法 | 今天的结果 |
|---|---|
| 用主渠道（便宜）做期望成本，贵渠道只是路由上的低优先级 | default 档售价**不**保证盖住贵渠道。流量一切过去就可能亏损。压力数字写在提案上，但不抬售价。 |
| 把 `fallback_probability_bps` 设得很小 | 期望成本接近便宜渠道。这是预测，不是上限。对方一整站故障时，实际回退比例可以是 100%。 |
| 同优先级两条不同成本，策略主渠道却填了便宜的那条 | 提案只看见主渠道。权重打到贵渠道的那部分流量不在公式里。 |
| 第三条更贵的渠道 | 公式看不见。风险列表也只查主和备（`service/pricing_control.go:723-726`）。 |

路由的优先级/权重和策略的主/备渠道 **没有代码关联**。管理员可以把售价按渠道 1 计算，请求却按优先级打到渠道 5。

### 3.3 建议的成本口径

在「售价只有一份」的前提下，底线用**可达集合里的最大成本**，不用加权平均，也不用「主渠道成本」。

对每个在售公开模型 M：

1. 找出所有销售分组 G，使得模型池允许 (G, M)，且存在启用渠道在 `abilities` 里对 (G, M) 启用。
2. 在这些渠道里，取报价成本（校准优先，否则该渠道记录的上游分组倍率）的**最大值**，当作压力成本。
3. 期望成本可以继续用主渠道，或用运营填写的回退概率做加权，只用于展示「正常时的毛利」。
4. **售价地板 = 压力成本 × (1 + overhead) / (1 - 最低毛利)。** 现网手写售价低于地板时，告警并建议下架该模型或摘掉那条贵渠道。不要自动改表达式。
5. pro 专用的贵渠道不进入 default 的可达集合（渠道的 `group` 不含 default，或模型池挡住）。default 的地板只看 default 能走到的渠道。pro 的地板单独算。因为倍率都是 1，**对外售价必须同时高于两边的地板**。做不到时，要么不让 pro 走那条贵渠道，要么提高 pro 的 `GroupRatio`（影响 pro 的全部模型）。

`stable` 档已经有「对备用渠道做最低毛利地板」的一半逻辑，但只认一个备用 id，而且发布路径不用 stable 档。P1 应把地板的输入从「一个备用 id」改成「该销售分组可达渠道的最大成本」，并且让 default 档的**告警**使用这个地板。告警不等于发布。

观测成本（日志校准、`ObservedGroup`）用来核对「钉死是否真的钉住」，不用来当售价地板。校准样本来自过去流量。过去流量若走的是 auto，校准倍率是混合值，不能代表钉死之后的成本。钉死并切流之后，旧校准在过期前会盖住新的分组倍率（校准优先，`pricing_control.go:354-356`）。**切换当天要看校准的 stale 窗口**（代码默认 96 小时，`pricing_calibration.go:62`）。窗口内若旧校准仍生效，提案会沿用 auto 时代的混合倍率。处理办法是切流后把受影响模型的旧校准删掉或等它过期，再让新同步的分组倍率生效。删除接口已有 `DeleteUpstreamCostCalibration`（`model/pricing_control.go:824` 一带）。这是操作，不是新代码。

### 3.4 和提案 / 审批的关系

链条保持：同步报价 → 重算提案（pending）→ 人批准 → 人发布。`compose.release.yml:40` 现在是 `PRICING_AUTO_PUBLISH: ${PRICING_AUTO_PUBLISH:-false}`。站主要求保持关闭。本方案同意，并且在第 3.3 节的地板做成「只告警」之前，也不要点手工发布去覆盖 v2.3 表达式。

原因已经在 v2.3 文档里写过，代码仍是这样：`pricingChangeForProposal` 生成的表达式只有 `p` 和 `c` 两项。自动发布另外有 `pricing_shape` 跳过（复杂表达式不写），但**手工点发布没有这个形状检查**（`PublishPricingProposal` 直接 `UpdateModelPricing`）。人如果批准后发布，一样会把带 `cr` 和长上下文的表达式打成两段式。

多渠道上线后，提案的正确用法是：

- 看期望成本、压力成本、`upstream_group` 是否等于密钥分组。
- 售价低于地板：下架模型或禁用那条渠道，然后拒绝提案。
- 不把提案发布到 `billing_expr`，直到有单独的「保形更新」实现（P2）。那不是本方案的范围。

`PRICING_AUTO_PUBLISH` 即使将来打开，也只发布 default 档、且涨跌幅在带宽内、且形状是简单两段式的模型（`autoPublishSkipReason`，`pricing_control.go:1128-1176`）。它有 `below_cost` 检查，比较的是提案自己的压力成本。压力成本今天只等于**一个**备用渠道。自动发布解决不了「路由上还有第三条更贵的渠道」。所以开关保持关闭不是保守口号，是现有检查覆盖不到新拓扑。

## 4. 可靠性

### 4.1 健康检查

| 机制 | 现在 | 多渠道下怎么用 |
|---|---|---|
| 管理端单渠道测试 | 一个模型 | 每条钉死渠道设 `test_model`。上线切换前对**该渠道模型列表**做目录级复测，不要用单模型绿灯代替 49 个模型。上次 21/49 说明目录级失败率很高，单模型测试会漏。 |
| 定时渠道测试 | 默认关 | P0 保持关。拆开并人工复测通过后，再用 `passive_recovery` 或低频 `scheduled_all`。探测失败会禁用**整条**渠道。 |
| 请求路径自动禁用 | 默认关；打开后默认仅 401 和余额类文案 | 拆渠道之后可以开总开关。不要把 503 加进禁用状态码：上游整站抖动时，所有钉死渠道会在几分钟内被一起关掉，恢复还要等探测。503 留给重试（同分组的第二把密钥）和人工。 |
| 超时禁用 | 探测慢于阈值也可禁用 | 默认 5 秒对推理偏紧。打开定时测试前把阈值放到真实流式的量级，否则慢模型把渠道打禁用。 |
| 重新启用 | 探测成功且自动启用开关打开 | 先确认生产 `MEMORY_CACHE_ENABLED`。若为 true，恢复后还有最多一个 `SYNC_FREQUENCY`（默认 60 秒）的路由空洞，见 §1.7。P1 修。 |

### 4.2 没有熔断器

一次 401 可以禁用整条渠道；一串 503 却既不禁用也不换站（除非已经配置了第二优先级**并且** `RetryTimes >= 1`）。这是两极，不是熔断。

P0 不新写熔断器。用拓扑补：

- 模型族拆开，一个族的故障不禁用其他族。
- 同一上游分组两把密钥、同一优先级、`RetryTimes=1`，应付单密钥失效。两把密钥若共享 dddai 账户余额，账户级「余额不足」会两把一起死。第二把密钥只有在独立额度或至少独立 401 时才有用。账户级余额要靠余额告警（第 5 节），不靠重试。
- 整站故障：P0 不接贵分组兜底。接受这段时间 503，和今天单渠道的行为相同，但不会在故障时改走 4.8 倍成本的池子。第二个站点是 P2，而且那个站点的成本必须先过地板。

P2 再考虑按渠道的错误率窗口（例如 1 分钟内 5xx 超过阈值则短暂摘除，冷却后探测恢复）。不要在 P0 用「第一次 5xx 就禁用」代替它。

### 4.3 降质池

`codex-plus` 这类池子返回 200 时，重试、禁用、渠道测试都认为健康。性能指标记的是成功和延迟，不记回答是否降质（`pkg/perf_metrics/metrics.go:45-54` 只有 model、销售分组、延迟、TTFT、成功、输出 token）。所以降质池不能靠现有健康检查挡。唯一可靠的挡法是不把该密钥放进启用渠道。

### 4.4 失败记在哪条渠道上

| 记录 | 有没有渠道 id | 说明 |
|---|---|---|
| 错误日志 `RecordErrorLog` | 有，`controller/relay.go:428` 写入 `channelError.ChannelId` | 响应头之前的失败能按渠道查。 |
| 消费日志 | 有渠道 id（结算发生在选中渠道之后） | 流式中途断开若被当成成功，会记在这条渠道上，但是成功单，不是错误单。 |
| `use_channel` | 有，重试路径会打「重试：id->id」 | `RetryTimes=0` 时通常只有一个 id。 |
| 性能指标 | **没有**渠道 id。键是模型 + 销售分组 | 同一模型走两条渠道时，成功率和延迟混在一起。看不出是哪条上游分组差。 |

### 4.5 和 PR #17 的关系

PR #17（`feat/model-status`，打开中）给性能指标加了：错误分类（客户端 400、配额、鉴权、审核不再算成模型不可用）、探针调度（默认关）、管理员视图、公开 v2（默认关）、保留期清理。探针令牌名默认 `ob-probe`。公开接口在旗标关闭时字段形状保持旧版。

它仍然按**模型 + 销售分组**聚合，不按渠道。探针打出去会再走一遍普通选路，所以：

- 渠道还是一把 `auto` 密钥时，探针测到的是 dddai auto 当时落到的池子，不能代表钉死之后的质量。
- 同一模型有多条渠道时，探针的一次失败会计进这个模型，分不清渠道。
- `public_v2` 若在多渠道之前打开，状态页上的可用率是混合值。

建议：PR #17 可以按它自己的节奏合并，但 **`probe_enabled` 和 `public_v2` 在「钉死渠道 + 指标能按渠道分开」之前保持关闭**。按渠道拆指标是 P1，要改的是 PR #17 正在动的 `pkg/perf_metrics` 和表结构。不要在本方案里另起一套探针。等 #17 合并后，在它的样本上加 `channel_id`（或管理员查询按渠道过滤），探针请求固定打到要测的那条渠道（已有管理员指定渠道的 pin，普通探针令牌没有）。公开 v2 仍等观察清单，不因为多了渠道就提前开。

## 5. 运维

### 5.1 余额

`channels.balance` 是我们库里的一列，单位注释写 USD（`model/channel.go:37`）。更新入口 `controller/channel-billing.go:457-496`：类型 60 **不在**已实现的分支里，落到 `default`，返回「尚未实现」。多密钥渠道直接拒绝查询（同文件 545-550）。全量更新 `updateAllChannelsBalance` 只有在设置了 `CHANNEL_UPDATE_FREQUENCY`（分钟）时才会定时跑（`main.go:122-127`）；余额 ≤ 0 且查询成功时会按自动禁用处理。类型 60 查询失败被 `continue` 掉，不会禁用，也不会告警。

这就是另一位代理在做的「用上游 access token 查 NewAPI 余额」。本方案不写第二套。落地前：

- 管理端「更新余额」对渠道 #1 和新建的类型 60 都会失败。不要把它当成已有监控。
- 低余额告警在代码里不存在（没有阈值、没有按渠道通知，除了余额查询成功且 ≤ 0 时的禁用）。
- P0 的余额监控是人工看 dddai 后台，或等那项功能合并后再打开 `CHANNEL_UPDATE_FREQUENCY`。合并后每条钉死渠道各自有余额。若多把密钥共用一个 dddai 账户，余额数字会重复，告警会响多次，那是预期，不是故障。
- 余额接口若返回的是人民币或对方的额度单位，不能直接和列注释里的 USD 比大小。那项实现要写明单位。在单位确认前，不要用 `≤ 0 就禁用` 这条旧逻辑套到新接口上。

### 5.2 密钥轮换

| 场景 | 做法 |
|---|---|
| 同一上游分组换一把新密钥 | 可以暂时做成第二条渠道，同一优先级、正权重，确认有流量后再禁用旧渠道。不要把两把不同分组的密钥做成多密钥模式。 |
| 多密钥轮询 | 代码支持（`ChannelInfo.MultiKeyMode`）。定价、余额、能力都是渠道级。只在「同一分组、同一价格、同一模型列表」时使用。余额查询目前跳过多密钥。 |
| 泄露或 401 | 禁用该渠道（或该密钥）。同优先级的另一把会接住，前提是 `RetryTimes >= 1`。否则当前请求失败，下一请求才会躲开已禁用渠道。 |

### 5.3 模型列表同步

每条渠道自己拉上游模型并写入 `channels.models`，然后重建能力。另一位代理负责：上游已删除的名字要剪掉，同一条渠道里的重复名字要去掉。

本方案额外的约束，留给那次实现或之后的人工核对，不在这里改代码：

- 剪掉名字之后，能力行必须跟着删。否则路由仍会把请求打到上游已经没有的模型上。现有 `AddAbilities` 是按当前 `models` 重建的；只要同步走的是这条重建，而不是只改字符串，就是安全的。实施那项改动时要确认走的是重建。
- 不要按「公开模型名全局唯一」去剪。渠道 A 和渠道 B 都有 `gpt-6-sol` 是有意的。
- 钉死分组的密钥拉 `/v1/models` 时，对方可能仍返回全站模型，而不是该分组 `enable_groups` 的子集。若如此，模型列表会比该密钥真正能跑的更大，请求会 503，报价同步却可能把「列表里有、但该分组倍率为空」的模型跳过并告警（`resolveUpstreamGroupRatio` 在没有候选时跳过该模型）。上线时以报价同步的警告为准核对模型列表，不要盲信 `/v1/models`。这一点要等有效分组解析那项工作的实际返回再确认。本次没有用钉死密钥打过 `/v1/models`。

### 5.4 管理端缺口

今天的界面能做：建渠道、填模型、分组、优先级、权重、映射、测试一个模型、看定价策略的主/备渠道、看提案。

今天的界面不能做，或会误导：

| 缺口 | 影响 | 阶段 |
|---|---|---|
| 渠道上没有「上游分组」字段。分组只活在对方密钥上 | 管理员无法核对这条渠道到底钉的是哪一组。P0 用渠道**名字和备注**写明分组。P2 再加只读字段（由同步写入，不要手填两套） | P0 用备注；P2 字段 |
| 策略主渠道和路由优先级各填各的 | 售价和真实流量脱节 | P1 告警 |
| 类型 60 余额按钮失败 | 见 §5.1 | 并行工作 |
| 性能页不按渠道拆 | 见 §4.4 | P1，跟 PR #17 |
| 渠道测试不等于目录测试 | 21/49 这种结果在健康检查里看不见 | P0 人工目录复测；P2 才考虑按渠道的多模型探测 |
| 发布按钮不区分「简单表达式」和「带缓存的 v2.3 表达式」 | 点下去会丢档 | P0 纪律：不点发布。P2 保形发布 |

## 6. 暗坑（按严重度）

严重度：S1 会在放量时亏钱或全站不可用；S2 会在部分流量上亏钱、少收钱或长时间故障；S3 是运维误判。

### S1

1. **auto 密钥的成本和质量都不可控。** dddai `auto_groups` 从 `codex-plus`（可能降质，0.15）走到 `openai-luna`（1.1）再到 `claude-max`（1.8，且限客户端）。我们发请求时选不了分组。定价若用 median，可能低于实际结算组；若生产仍是 `max`，则成本偏高，但运行时仍可能打到降质组。切换到钉死密钥之前，这是现网状态，不是假设。
2. **路由可达的渠道集合 ≠ 定价的主/备渠道。** default 档售价不把备用渠道当地板（`pricing_control.go:425-428` 只对 `stable`）。再挂一条低优先级的贵渠道，提案可以仍显示健康毛利。故障时 100% 流量走贵渠道。
3. **整条渠道一起禁用。** 模型族还堆在渠道 #1 上时，一次 401 或一次余额关键词命中，所有模型同时消失。2026-10-11 的全站 503 是对方故障、我们没有第二条渠道；自动禁用若在拆渠道前打开，会制造同样的全站效果。默认禁用开关是关的，不要为了「更安全」先打开。
4. **重试不会换一条你没配上的渠道。** `retry` 超过优先级层数时夹在最低层（`channel_cache.go:165-167`），也不排除刚失败的渠道 id。`RetryTimes` 默认 0。把重试次数调到 5、但每个模型只有一条渠道，等于对同一条连打 6 次（0 到 5）。
5. **手工发布会毁掉 v2.3 表达式。** `pricingChangeForProposal`（`pricing_control.go:840-845`）只写 `p` 和 `c`。v2.3 有 20 个模型带 cache-read。`PRICING_AUTO_PUBLISH` 必须保持 false；审批通过后也不要按发布，除非该模型的现网表达式本来就是这个两段式形状。

### S2

6. **流式中途失败当成功扣费，且不回退。** `OaiStreamHandler` 始终返回 usage 和 nil（`relay-openai.go:181-194`）。没有 usage 时用本地文本估算 completion。上游可能已按完整生成扣我们的钱，我们却按截断文本收用户的钱，或者相反。校准能在几天后修正**报价系数**，不能修正这一次的路由。回退设计不能假设「流失败了会换渠道」。
7. **`GroupRatio` 两边都是 1。** pro 走 `openai-pro`（0.36）、default 走 `default`（0.23）时，用户付的钱一样，成本差约 1.57 倍。模型池只决定 pro 能不能看见某个模型，不决定单价。贵路径要单独过地板。
8. **旧校准盖住新分组。** 校准优先于 `upstream_group_ratio`，默认 96 小时内仍可用。从 auto 切到钉死分组后，提案会继续用混合倍率，直到校准过期或被删掉。
9. **`model_mapping` 与报价的方向相反。** 计费用公开名，报价同步用「上游名 → 第一条公开名」。两条渠道映射不一致时，成本行可能记到错误的公开模型上，售价对不上那次上游实扣。P0 尽量不使用映射：公开名与上游名保持一致。必须映射时，一条渠道内一个上游名只对应一个公开名。
10. **预扣费用的是切换前的销售分组，结算用切换后的。** 代码有追加预扣（`PrepareTieredBillingForSelectedGroup`）。若令牌是销售侧 `auto`，并且 AutoGroups 里同时有 default 和 pro，用户可能被按 pro 的渠道服务、仍按倍率 1 付钱。现网倍率相同所以金额碰巧一样，渠道却可能更贵。上线前令牌分组留空（跟随用户分组），不要给 default 用户发 `group=auto` 且把 pro 放进 AutoGroups。
11. **类型 60 没有余额更新。** 上游钱包到 0 时，我们不会提前禁用。表现是大面积 401 或「quota」文案。若那时自动禁用已打开，所有钉死渠道会依次被禁用。余额功能落地前，这是人工值班项。
12. **504/524 不重试。** 网关超时不会换备用密钥。长生成更容易撞上。备用渠道帮不上这类错误。
13. **渠道 `group` 列是 `varchar(64)`。** `default,pro` 没问题。以后销售分组变多，字符串会截断或直接写不进去。P0 只有两个分组，记一笔即可。

### S3

14. **权重 0 不是「不参与」。** 全 0 时大家权重变 100；有人非 0 时，0 权重的渠道可能让选择落到 `channel not found`。
15. **自动启用后的内存路由空洞。** 仅当 `MEMORY_CACHE_ENABLED=true`。最长约一个同步周期。生产是否开启未知。
16. **渠道测试绿灯 ≠ 模型可用。** 只测一个模型。21/49 不会出现在这条任务的成功数里。
17. **性能指标混渠道。** 用状态页判断「这个模型不稳」会误伤另一条健康渠道，或反过来把降质池的 200 算进可用率。
18. **代码默认分组名仍是 vip。** 新环境或重置 options 会和现网 default/pro 不一致。生产 options 本次未读。
19. **`GetGroupRatio` 缺键返回 1 并只打日志。** 分组名写错时，用户按 1 倍付款，不会拒绝请求。渠道分组写成不存在的名字时，能力行在，倍率却是 1。
20. **多密钥与定价的组合。** 同一渠道多把密钥若实际上是不同分组（有人在 dddai 改了其中一把的 group），报价仍是一行。运行时成本会随轮询跳动，提案看不见。

## 8. 需要站主拍板的问题

下面每一条都会改变 P0 的配置。没回答之前，方案按**较严的默认**执行：不挂贵回退、不启用 openai-pro / claude-api、RetryTimes 维持 0、自动禁用保持关、不发布提案。

1. **pro 要不要单独走 `openai-pro`（0.36，对方称不降质）？** 若要，接受两种之一：对外售价提高到能覆盖 0.36 这条路径（default 用户也会变贵，因为倍率都是 1 且售价只有一份），或者只提高 `GroupRatio.pro`（pro 的全部模型变贵，不只是 GPT）。不算过 P0-4 之前不启用这条渠道。
2. **`claude-api` 要不要买？** 它不在 auto 里，倍率未知。opus 4-6/4-7/4-8 和 sonnet 4-6 如果必须卖，就先建钉死密钥、拉报价、过地板，再启用。不必须卖，P0 就不要这条渠道。
3. **`codex-plus` 是否允许作为任何自动路径？** 建议：不允许。若你接受降质换低价，它只能是**唯一**渠道且售价按 0.15 重新算，不能和 `default` 0.23 混在同一优先级，也不能当回退（回退时用户没有选择权）。
4. **同分组要不要第二把密钥？** 没有的话，P0 的故障行为和今天一样（该模型族 503），只是不会误伤其他模型族，也不会在故障时走贵池。有的话，两把密钥必须仍是同一上游分组，并把 `RetryTimes` 设为 1。
5. **现网 `PRICING_GROUP_RATIO_POLICY` 是否仍是整改记录里的 `max`？** 本次没读 `.env`。钉死同步落地后应停用 max/median，改为「用该渠道密钥的分组」。切换前不要用 max 的成本去判断 P0-4，否则会把卖得了的模型误判成亏损，或反过来。
6. **最低毛利地板用 v2.3 的 60%，还是渠道价池那 6 个模型的 13% 例外仍然有效？** P0-4 的表必须按你的选择算。本方案不知道那 6 个模型今天是否仍在售。
7. **放量前是否接受「整站级上游故障 = 该站模型全部 503」，直到有过了地板的第二站点？** 建议接受。用 `openai-luna` 或 `enterprise` 做兜底会在故障当天亏损。
8. **PR #17 的探针和公开 v2，是否同意在渠道维度做完之前保持关闭？** 建议关闭。
9. **第二个上游站点有没有候选、准备什么时候接？** 没有的话 P2-4 保持不做，文档里的优先级 80 只是以后的模板。

## 9. 和并行工作的边界

| 并行项 | 本方案怎么用 | 不要在本方案里做 |
|---|---|---|
| 同步时剪掉已删除和重复的渠道模型 | 剪的是单条渠道的 `models`。跨渠道同名必须保留 | 不另写同步逻辑 |
| NewAPI 余额（上游 access token） | P0 用人工查看；落地后按渠道告警，并先确认单位 | 不在 `updateStandardChannelBalance` 里夹一套临时实现 |
| `/api/pricing` 的有效上游分组 | 钉死渠道的报价必须以密钥分组为准。P0-3、P0-5 等它 | 不改 `pricingGroupRatioPolicy` 的四种策略来模拟钉死 |
| PR #17 模型状态 | 旗标保持关。P1-5 在它的样本上加渠道，而不是新探针 | 不改公开 v1 的字段形状 |

## 11. 建议的切换顺序（仍是配置）

1. 建好钉死密钥和渠道，模型列表先只放 1 个已核对模型，优先级 100，销售分组先用一个内部测试用户所在的分组。
2. 测试用户打这个模型，日志渠道 id 是新渠道，对方侧分组正确。
3. 报价同步显示该模型的 `upstream_group` 正确，成本低于现网售价地板。
4. 把该模型从渠道 #1 的模型列表去掉（或整条 #1 降低优先级），再打一次，确认不会回到 #1。
5. 按族重复。每族独立，失败就停在该族，不要一天内把 49 个模型同时换完。
6. 全部族通过目录复测后，禁用 #1，再考虑同分组第二密钥和 `RetryTimes=1`。
7. 全程不点定价发布，不打开自动发布。
